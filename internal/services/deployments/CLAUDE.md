# Deployments service notes

Load-bearing details for `internal/services/deployments/`: the `anthropic_deployment` resource and the `anthropic_deployment_runs` data source (Managed Agents beta, `client.Beta.Deployments` / `client.Beta.DeploymentRuns`, standard API key). The root `CLAUDE.md` still applies; where a note here says "see above" or "see below" and the target is not in this file, it is a section of the root `CLAUDE.md`. Record new details about this service here, not in the root file.

**Resources:**
- `anthropic_deployment` (`internal/services/deployments/deployment_resource.go`) — manages a scheduled deployment: binds an agent, an environment, initial events and an optional cron schedule to run Managed Agent sessions autonomously (Beta managed-agents API; `client.Beta.Deployment`); standard API key; `initial_events`, `resources`, `budget` are `jsontypes.Normalized` raw-JSON attributes (unmarshalled into the SDK's typed union params rather than modeled as native nested blocks — the union depth wasn't worth it); `agent_id` only supports the plain agent-ID string SDK variant (re-pins to latest on every send), never the `{id, version}` pinned variant; `metadata` Update goes through `buildMetadataPatch` + `SetExtraFields` like vaults; `paused` is reconciled via the separate Pause/Unpause endpoints, not the main Update body; no hard-delete endpoint — destroy always archives (same as `anthropic_service_account`), so every acceptance run leaves one archived deployment in the test workspace, but unlike that resource this one **does** run in CI (standard API key, no OAuth gate); `Update` applies the same defensive read-after-write consistency wait as vaults; a `github_repository` token goes through the write-only, sensitive `repository_authorization_tokens_wo` map (keyed by repository `url`, rotation via `repository_authorization_tokens_wo_version`), read from `req.Config` and merged into the Create and Update `resources` (resent on every update: measured live on 2026-11-24, the API answers 400 `github_repository resources require an authorization_token` to any `github_repository` sent without a token or with `""`, **public repositories included** despite the SDK comment "optional for public ones", on create and on update; a fake token is accepted, so the API does not check it with GitHub; an update without `resources` keeps them), while `deploymentRepositoryTokenValidator` rejects an `authorization_token` key anywhere inside the non-sensitive `resources` JSON, at any depth and in any letter case (the SDK silently drops a misspelled or nested one, which still lands in the plan), and `applyRepositoryTokens` fails Create/Update on a token whose URL matches no repository (the validator cannot check it when `resources` is unknown at plan); the validator and `applyRepositoryTokens` therefore also reject a `github_repository` without a token (`Missing repository token`, naming the URLs, which are not secret; it covers an imported deployment too), the validator a null or empty token value (checked again at apply in `repositoryAuthorizationTokens`), and a `resources` value it cannot decode (it decodes with `UseNumber`, since `jsontypes.Normalized` accepts `1e400` and a plain `json.Unmarshal` does not; on that error the token keys are not matched, so the error is not doubled); no diagnostic quotes a key of the token map, which may be a token in a map written the wrong way round: unmatched keys are reported by count, with the repository URLs of `resources` (Claude Security finding find_01HpvBfpgvSBZUVWcu4PCJAp); the API never returns the token (SDK v1.84.0 `BetaManagedAgentsGitHubRepositoryResourceConfig` doc comment), so `resources` in state matches the token-free configuration: measured live on 2026-11-24, the API echoes a `github_repository` element as sent, without filling `checkout` or `mount_path`, and the template example converges (apply, update, empty plan) with the provider built locally

**Data sources:**
- `anthropic_deployment_runs` (`internal/services/deployments/deployment_runs_data_source.go`) — lists the run history of scheduled deployments (`GET /v1/deployment_runs`, **not** `/v1/deployments/{id}/runs`) with optional `deployment_id`, `has_error` and `trigger_type` filters and transparent pagination; `session_id` and `error` are mutually exclusive (one is always null). A well-formed but unknown `deployment_id` (`depl_` + 24 base62 characters, e.g. `depl_01AAAAAAAAAAAAAAAAAAAAAA`) returns 200 with an empty list, but a malformed one (`depl_01xyz` from the public docs, or all zeros) is rejected with `400 Invalid deployment ID` — verified live 2026-09-21; the example and native test rely on the former so they apply for real without any deployment in the test workspace
