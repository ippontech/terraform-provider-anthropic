# Agents service notes

Load-bearing details for `internal/services/agents/`: the `anthropic_agent` resource and the `anthropic_agent` / `anthropic_agents` data sources (Managed Agents beta, `client.Beta.Agents`, standard API key). The root `CLAUDE.md` still applies; where a note here says "see above" or "see below" and the target is not in this file, it is a section of the root `CLAUDE.md`. Record new details about this service here, not in the root file.

**Resources:**
- `anthropic_agent` (`internal/services/agents/agent_resource.go`) — manages Managed Agents (create/read/update/delete); tool permissions are security-relevant, so `Read` never filters what the API returns: `mapMCPToolsetsToState` keeps state order for tracked toolsets and appends any other toolset, and `mapToolConfigsToState` (shared by `agent_toolset.configs` and `mcp_toolsets[*].configs`) appends per-tool configs for untracked tools (for a toolset already in state, except one whose `enabled` and `permission_policy` both equal the toolset defaults and that sets no web option (`apiToolConfig.setsExtra`: a web option has no inherited default), which changes nothing and would otherwise leave a diff that never clears if the API lists such configs; a toolset not in state yet, as on import, maps every config verbatim so ImportStateVerify holds) and keeps an unset `enabled`/`permission_policy` null only while the API value equals the toolset default it inherits, so an out-of-band per-tool override (e.g. an `always_allow` on one MCP tool) shows up as drift on refresh, while an echoed default does not cause a perpetual diff (`TestAccAgentResource_withAgentToolset` checks the echo live); every permission policy attribute takes `always_allow`, `always_ask` or `auto` (the server evaluates each call: runs, denies or asks; not a human checkpoint, the template says so). Create and Update map with `applyMapping` instead: no MCP toolset or per-tool config the plan lacks is added and a per-tool field the plan leaves null stays null, since `mcp_toolsets` and `configs` are not Computed and Terraform rejects any other value as an inconsistent result after apply; the next Read shows the difference. A toolset `default_enabled`/`default_permission_policy` left unset is planned from a schema `Default`, the API's documented default (`true`; `always_allow` for `agent_toolset`, `always_ask` for `mcp_toolsets[*]`), rather than kept from refresh, so an out-of-band change to it (to `always_allow`, say) shows as a diff and the apply reverts it, and the unset per-tool fields inherit the restored default ([#499](https://github.com/ippontech/terraform-provider-anthropic/issues/499)). The values come from the permission policies page and the agents create/update reference (read 2026-10-30), not from a live call: `TestAccAgentResource_toolsetDefaults` checks them against the API (it lets the API resolve its own defaults out of band and expects an empty plan). Framework v1.19.0 applies a `Default` to an attribute nested in a list too; `TestAgentResource_toolsetDefaultsPlan` proves it through the framework's own `PlanResourceChange` (`providerserver` serving the resource alone), along with a state written before the defaults planning no change. On Update, `updateToolsParams` sends `configs: []` for every toolset planned without per-tool configs (null or empty), as Update does for `skills`: the update reference calls `tools` a full replacement but says nothing about an omitted `configs`, and if the API kept the stored overrides, one set out of band (which Read reports) would survive every apply ([#508](https://github.com/ippontech/terraform-provider-anthropic/issues/508)). The SDK's `omitzero` drops a nil slice but sends an empty one as `[]` (`TestAgentResource_toolsetConfigsOnUpdate` checks the body). Create still omits the field: nothing is stored yet. The `web_fetch`/`web_search` entries of `agent_toolset.configs` also take `allowed_domains` xor `blocked_domains` (sets, 1-64), `max_content_tokens` and `url_sources` (`web_fetch`) and `user_location` (`web_search`, sent with `type = approximate`) (`agent_web_tools.go`): `agentToolConfigsValidator` rejects an option on another tool at plan time, `buildAgentToolConfigParams` rejects it again at apply, `uniqueDomainsValidator` rejects at plan time two entries of one list that are the same domain under `domainKey` (the docs allow a domain once per list; stored normalized, they would fail the apply as an inconsistent result), and the response maps them through `apiToolConfig.extra` (the API documents a default only for `url_sources`, see below), resolved against the plan or prior state by `webToolOptionsToState`: a domain set equal under the API's comparison (`domainKey`: the hostname ignores case, a `web_search` path suffix keeps it, a trailing `/` is ignored) keeps the configured spelling, and with `applyMapping` an option or `user_location` field the plan leaves null stays null (neither the echo nor the absence of defaults is verified live yet; `TestAccAgentResource_withAgentToolset` leaves every option unset in at least one step, so its empty post-apply plan checks both, as it does for `enabled`); built-in and MCP config entries now have different object types (`agentToolConfigModel` vs `agentMCPToolConfigModel`) and `mapToolConfigsToState` reads the current list attribute by attribute; `url_sources` (SDK v1.79.0) has `user_input` (`all`/`none`) and two tool-result filters (`type` `all`/`none`/`only`/`except`, `tools` a set of names exactly for `only`/`except`): every key is sent in the object form the API answers in (an explicit `all` is sent, not dropped); `all` is the documented default of each key, so Read maps a key at `all`, and an object left with no key, to null, `urlSourcesToState` keeps a configured `all` whether the API echoes or omits it, and with `applyMapping` a key the plan leaves null stays null, Read also accepts the string shorthand, and `validateURLSources` rejects an empty object and all three keys `none` (an API rule) at plan time. `uniqueMCPServerNamesValidator` rejects two `mcp_toolsets` entries for one server; `model_effort` (Optional+Computed, API fills a per-model default) and `model_inference_geo` (Optional, free-form) sit next to `model_speed`: the API replaces `model` as a whole on update (omitting `inference_geo` clears it; omitting `effort` keeps the stored value only if `id` is unchanged, else resolves the new model's default), and the provider follows that: `buildModelConfigParams` always sends the full object, sends `effort` only when the plan knows it, and omits a null `model_inference_geo` (which clears the pin); `modelEffortFollowsModel` (plan modifier, replaces `UseStateForUnknown`) reuses the state effort only while `model` is unchanged and leaves it unknown otherwise, so changing `model` without `model_effort` resolves the new model's default; `multiagent` (coordinator roster, `agent_multiagent.go`) is an Optional single-nested attribute whose `agents` entries are `agent`/`self`/`advisor`. The API resolves `self` into an `agent` entry carrying the coordinator's own ID and echoes `advisor` last, so `mapMultiagentToState` correlates the API roster with the planned/prior roster **by key, never by index** (agent by `id`, advisor by type, self last as the owner-ID entry no explicit `agent` entry claimed), keeps config order and `self` as configured, and appends unmatched API entries as drift; with no prior roster (import) it maps verbatim, so `self` reads back as `agent` with the owner's ID. Only `version` is Computed (never the list or object). Clearing the block sends `multiagent: null` through `SetExtraFields` (only when state had one); the data sources map verbatim. Since SDK v1.80.0 the response `multiagent` is a union with `multiagent_20261001`, which the provider does not manage yet: `multiagentRosterFromAPI` reads it best-effort (predefined subagents as `agent` entries, then an enabled advisor as `advisor`; inline agents and workflows are not represented) and adds an `Unsupported multiagent type` warning naming the agent, never an error; `execution_identity` (SDK v1.81.0, `agent_execution_identity.go`) is `service_account` (no identifier, the default) or `aws_role` + `role_arn` (Claude Platform on AWS, required there before a deployment can use the agent): the API returns `service_account` for every agent, so `mapExecutionIdentityToState` keeps that default null while the configuration leaves it unset and maps anything else (an out-of-band IAM role) as drift; `buildExecutionIdentityParams` sends a configured value, omits a null one unless state had one (then it sends `service_account`, which the update reference says restores the default), so configurations without it keep their request body; the data sources map it verbatim

**Data sources:**
- `anthropic_agent` (`internal/services/agents/agent_data_source.go`) — fetches a single agent
- `anthropic_agents` (`internal/services/agents/agents_data_source.go`) — lists all agents

## Agent built-in tool configs are an SDK union

Since SDK v1.66.0 `agent_toolset.configs` maps to `BetaManagedAgentsAgentToolConfigParamsUnion` — one struct per built-in tool, so the Terraform `name` attribute selects a union branch instead of filling an enum field. Two places must stay in sync when the API gains a built-in tool: the `stringvalidator.OneOf(...)` list on the `name` attribute and the `switch` in `buildAgentToolConfigParams` (`internal/services/agents/agent_resource.go`). The helper returns an error diagnostic on an unknown name rather than silently sending an empty config. Note where each net catches: the validator rejects a name outside the `OneOf` list **at plan time**, but a name that passes the validator and has no `switch` branch is only reached from `Create` and `Update`, so it fails **mid-apply** — which is why the branch coverage in `agent_resource_internal_test.go` matters. Permission policies are the three `always_allow` / `always_ask` / `auto` shapes (`auto` since SDK v1.72.0, #273), wrapped in each tool's, each MCP tool config's and both toolset defaults' own `PermissionPolicyUnion`: every builder fills its union's `OfAlwaysAllow`/`OfAlwaysAsk`/`OfAuto` from `permissionPolicyParams`, so a fourth policy means one `case` there plus `permissionPolicyValidator`. The response side reads the policy as the union's plain `type` string, so `mapToolConfigsToState` needs no change for a new policy.

Response-side types stay flat (`...AgentToolConfigUnion`), so state mapping needs no per-tool switch. A per-tool option (the web options) lives only on its tools' branches, so it needs a row in `webToolOptionTools` (`agent_web_tools.go`), which both the plan-time validator and `buildAgentToolConfigParams` read.
