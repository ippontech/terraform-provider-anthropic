# Agents service notes

Load-bearing details for `internal/services/agents/`: the `anthropic_agent` resource and the `anthropic_agent` / `anthropic_agents` data sources (Managed Agents beta, `client.Beta.Agents`, standard API key). The root `CLAUDE.md` still applies; where a note here says "see above" or "see below" and the target is not in this file, it is a section of the root `CLAUDE.md`. Record new details about this service here, not in the root file.

**Resources:**
- `anthropic_agent` (`internal/services/agents/agent_resource.go`) — manages Managed Agents (create/read/update/delete); tool permissions are security-relevant, so `Read` never filters what the API returns: `mapMCPToolsetsToState` keeps state order for tracked toolsets and appends any other toolset, and `mapToolConfigsToState` (shared by `agent_toolset.configs` and `mcp_toolsets[*].configs`) appends per-tool configs for untracked tools (for a toolset already in state, except one whose `enabled` and `permission_policy` both equal the toolset defaults, which changes nothing and would otherwise leave a diff that never clears if the API lists such configs; a toolset not in state yet, as on import, maps every config verbatim so ImportStateVerify holds) and keeps an unset `enabled`/`permission_policy` null only while the API value equals the toolset default it inherits, so an out-of-band per-tool override (e.g. an `always_allow` on one MCP tool) shows up as drift on refresh, while an echoed default does not cause a perpetual diff (`TestAccAgentResource_withAgentToolset` checks the echo live); every permission policy attribute takes `always_allow`, `always_ask` or `auto` (the server evaluates each call: runs, denies or asks; not a human checkpoint, the template says so). Known gap: a toolset `default_enabled`/`default_permission_policy` left unset is Optional+Computed with no plan modifier, so an out-of-band change to it (even to `always_allow`) is kept from refresh with no diff, and the unset per-tool fields compared with it stay null too. Create and Update map with `applyMapping` instead: no MCP toolset or per-tool config the plan lacks is added and a per-tool field the plan leaves null stays null, since `mcp_toolsets` and `configs` are not Computed and Terraform rejects any other value as an inconsistent result after apply; the next Read shows the difference. The `web_fetch`/`web_search` entries of `agent_toolset.configs` also take `allowed_domains` xor `blocked_domains` (sets, 1-64), `max_content_tokens` and `url_sources` (`web_fetch`) and `user_location` (`web_search`, sent with `type = approximate`) (`agent_web_tools.go`): `agentToolConfigsValidator` rejects an option on another tool at plan time, `buildAgentToolConfigParams` rejects it again at apply, and the response maps them through `apiToolConfig.extra` (the API documents no default for them), resolved against the plan or prior state by `webToolOptionsToState`: a domain set equal under the API's comparison (case-insensitive, trailing `/` ignored) keeps the configured spelling, and with `applyMapping` an option or `user_location` field the plan leaves null stays null (neither the echo nor the absence of defaults is verified live); built-in and MCP config entries now have different object types (`agentToolConfigModel` vs `agentMCPToolConfigModel`) and `mapToolConfigsToState` reads the current list attribute by attribute; `url_sources` (SDK v1.79.0) has `user_input` (`all`/`none`) and two tool-result filters (`type` `all`/`none`/`only`/`except`, `tools` a set of names exactly for `only`/`except`): every key is sent in the object form the API answers in (an explicit `all` is sent, not dropped; that the API echoes it rather than nulling it is unverified live, `TestAccAgentResource_withAgentToolset` checks it), Read also accepts the string shorthand, and `validateURLSources` rejects an empty object and all three keys `none` (an API rule) at plan time. `uniqueMCPServerNamesValidator` rejects two `mcp_toolsets` entries for one server; `model_effort` (Optional+Computed, API fills a per-model default) and `model_inference_geo` (Optional, free-form) sit next to `model_speed`: the API replaces `model` as a whole on update (omitting `inference_geo` clears it; omitting `effort` keeps the stored value only if `id` is unchanged, else resolves the new model's default), and the provider follows that: `buildModelConfigParams` always sends the full object, sends `effort` only when the plan knows it, and omits a null `model_inference_geo` (which clears the pin); `modelEffortFollowsModel` (plan modifier, replaces `UseStateForUnknown`) reuses the state effort only while `model` is unchanged and leaves it unknown otherwise, so changing `model` without `model_effort` resolves the new model's default; `multiagent` (`agent_multiagent.go`) is an Optional single-nested attribute of `type` `coordinator` (its `agents` roster, required, entries `agent`/`self`/`advisor`) or `multiagent_20261001` (`subagents`/`workflows` with `enabled`, `inline_agents_enabled` and a `predefined_agents` list of `agent`/`self` entries, plus `advisor { model }`), the attributes of the other type rejected by `multiagentConfigValidator`. The API resolves `self` into an `agent` entry carrying the coordinator's own ID and echoes `advisor` last, so `mapMultiagentToState` correlates the API roster with the planned/prior roster **by key, never by index** (agent by `id`, advisor by type, self last as the owner-ID entry no explicit `agent` entry claimed), keeps config order and `self` as configured, and appends unmatched API entries as drift; with no prior roster (import) it maps verbatim, so `self` reads back as `agent` with the owner's ID. Only `version` is Computed (never the list or object). Clearing the block sends `multiagent: null` through `SetExtraFields` (only when state had one); the data sources map verbatim. For `multiagent_20261001` the API merges an update into the stored object level by level (an omitted key keeps its stored value, a sent `predefined_agents` list replaces), so `buildMultiagent20261001Params` always sends every key, defaults included (`predefined_agents: []`, inline agents `enabled`, advisor `disabled`), and the stored object always ends up as planned; Read (`mapMultiagent20261001`) keeps a field or a whole setting the configuration leaves unset null while the API holds its default (subagents and workflows enabled with inline agents and no list, advisor disabled) and maps anything else as drift; both `predefined_agents` lists reuse the coordinator's by-key correlation (`correlateRoster`) and version pinning (`priorAgentVersions`, same list only); a validator requires at least one predefined agent when `inline_agents_enabled = false` (a documented 400); the data sources map every setting verbatim. Only a `multiagent` type the provider does not know still reads with an `Unsupported multiagent type` warning, never an error; `execution_identity` (SDK v1.81.0, `agent_execution_identity.go`) is `service_account` (no identifier, the default) or `aws_role` + `role_arn` (Claude Platform on AWS, required there before a deployment can use the agent): the API returns `service_account` for every agent, so `mapExecutionIdentityToState` keeps that default null while the configuration leaves it unset and maps anything else (an out-of-band IAM role) as drift; `buildExecutionIdentityParams` sends a configured value, omits a null one unless state had one (then it sends `service_account`, which the update reference says restores the default), so configurations without it keep their request body; the data sources map it verbatim. `metadata` updates go through `tfvalue.MetadataPatch` (the API applies metadata as a patch, https://platform.claude.com/docs/en/api/beta/agents/update; the update used to send `{}` for a removed block, which changed nothing); it shares the single `SetExtraFields` call with the `multiagent: null` clear. Request building is split per attribute (`buildCreateParams`, `buildUpdateParams`, `buildToolsParams` and the per-kind builders below it), and the response mapping shared with the data sources (`splitAgentTools`, `mcpServersValue`, `skillsValue`, `customToolsValue`, `keepNull`) is in `agent_response.go`; `mapAgentToDataSourceObject` reuses `mapAgentResponseToDataSource`, so the two data sources cannot drift apart. Fake-API tests: `agent_resource_*_fake_test.go`, `agent_data_source_fake_test.go` and `configure_fake_test.go`, with the routes and handlers in `fake_test.go`; the fake resolves only what the provider maps back (toolset defaults and inherited per-tool values for `mapToolConfigsToState`, pinned versions, `self` and the advisor echoed last for `mapMultiagentToState`, the default effort, the pinned skill version, the default `service_account` identity), each next to the provider function it serves; the API's validations and merges are not emulated, since the provider sends complete bodies that `AssertJSONBodies` pins

## Agent built-in tool configs are an SDK union

Since SDK v1.66.0 `agent_toolset.configs` maps to `BetaManagedAgentsAgentToolConfigParamsUnion` — one struct per built-in tool, so the Terraform `name` attribute selects a union branch instead of filling an enum field. The built-in tools live in one table, `builtinTools` (`internal/services/agents/agent_builtin_tools.go`): each entry holds the tool name, the web options it accepts and the function that fills its union branch. The `stringvalidator.OneOf(...)` list on the `name` attribute, the `agent_toolset` description, `webToolOptionTools` and `buildAgentToolConfigParams` all read it, so a new built-in tool is one entry. `buildAgentToolConfigParams` returns an error diagnostic on a name the table lacks rather than silently sending an empty config; the validator already rejects such a name **at plan time**, and only a name unknown at plan time reaches that check, **mid-apply**. Permission policies are the three `always_allow` / `always_ask` / `auto` shapes (`auto` since SDK v1.72.0, #273), wrapped in each tool's, each MCP tool config's and both toolset defaults' own `PermissionPolicyUnion`: every builder fills its union's `OfAlwaysAllow`/`OfAlwaysAsk`/`OfAuto` from `permissionPolicyParams`, so a fourth policy means one `case` there plus `permissionPolicyValidator`. The response side reads the policy as the union's plain `type` string, so `mapToolConfigsToState` needs no change for a new policy.

Response-side types stay flat (`...AgentToolConfigUnion`), so state mapping needs no per-tool switch. A per-tool option (the web options) lives only on its tools' branches, so it needs a row in `webToolOptionTools` (`agent_web_tools.go`), which both the plan-time validator and `buildAgentToolConfigParams` read.

## Plan-time model lifecycle check

`ModifyPlan` (`agent_model_lifecycle.go`) looks up `model`, `multiagent.advisor.model` and a coordinator roster's advisor entry with `client.Models.Get` (accepts an ID or alias, returns `lifecycle`, `deprecated_at`, `retires_at`: https://platform.claude.com/docs/en/api/models/retrieve). `deprecated` warns; `retired` is an error when the plan sets it (create, or a change to it: "Requests to retired models fail", https://platform.claude.com/docs/en/about-claude/model-deprecations) and a warning when the prior state had it in the same slot (matched by kind, not list index). Best effort: null/unknown values, destroys and every lookup failure (5s timeout, retries included) give no diagnostic, only `tflog.Debug`. Results, failures included, are cached per model in `providerdata.ModelInfoCache` via `pd.Models()`, one per provider configuration and never a package global (the framework builds a resource per request). Tests: a plugin-testing step plans four times, so it makes one lookup per model per plan; `agentsFake` serves `routeGetModel` (the models tests name are active, `setModel` changes one), and "no request at all" assertions must exclude that route.
