# `internal/services/compliance/` service notes

Load-bearing details for `internal/services/compliance/`. The root `CLAUDE.md` still applies; record new details about this service here, not in the root file.

**Resources:**
- `anthropic_compliance_settings` (`internal/services/compliance/compliance_settings_resource.go`) — organization-wide singleton turning the Compliance API (activity recording) on or off; `GET/POST /v1/organizations/compliance_settings` (Admin API, raw `admin.Client`, no `?beta=true`; not in SDK v1.67.0, added in 1.69.0); `state` is `enabled`/`disabled`, sent in the canonical object form `{"type": ...}` (the API also accepts the string shorthand, and `parseState` decodes both); `id` is the organization ID from `GET /v1/organizations/me`, resolved in Create and in ImportState, which accepts **any** import ID (with a warning naming the organization imported when the ID is not its ID). Read and Update (before its POST) resolve it again and fail when the admin key belongs to another organization than `id`: the singleton is addressed through the key alone, so nothing else would catch it. A POST that answers another state than the one sent is an explicit error (Create stores nothing, Update keeps the planned value), not Terraform's inconsistent-result error. Create adopts the singleton (the update is idempotent); Read never removes it, so a 404 is an error rather than a planned re-creation. **Delete is a no-op with a warning**, deliberately not a reset to `disabled`: turning it off stops activity recording and the missed activity is unrecoverable, so a destroy must not do it implicitly. Documented drift sources: an Access Transparency provisioning re-enables it after `disabled`, and an organization with a parent reads the parent's state.
