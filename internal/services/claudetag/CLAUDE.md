# Claude Tag service notes

Load-bearing details for `internal/services/claudetag/`: the `anthropic_claude_tag_slack_channel`, `anthropic_claude_tag_slack_workspace_settings` and `anthropic_claude_tag_bundle_target` resources and the `anthropic_claude_tag_bundle(s)`, `anthropic_claude_tag_slack_channel` and `anthropic_claude_tag_slack_workspaces` data sources. The root `CLAUDE.md` still applies; record new details about this service here.

Source of truth: the guide https://platform.claude.com/docs/en/manage-claude/claude-tag-api (read 2026-10-27). Comments cite its sections by anchor. Nothing here was checked against the live API: no Claude Enterprise organization with Slack is available.

**Transport.** 14 organization endpoints under `/v1/organizations/claude_tag/`, beta, Claude Enterprise only. SDK v1.84 has none of them (only SDK v2 does), so every call goes through `internal/admin` (`claudeTagRequest`) with `admin.WithBeta("experimental-claude-tag-2026-10-21")`; without the header every endpoint answers 404 as if it did not exist. The key is a Claude Enterprise scoped Admin API key in `admin_api_key` (`read:claude_tag` for GET, `write:claude_tag` for POST/DELETE; a Console key does not work). No `?beta=true` query flag is sent: the guide's cURL examples have none (the Plugins API does send it). Lists page with an opaque `next_page` passed back as `page` until it is null, `limit` 1 to 100 (`listAll`, which also errors on a cursor sent back unchanged); a find-by-Slack-ID request does not page (`lookup`).

**Slack's own IDs live under `slack`.** The API gives `slack_channel_id` and `slack_workspace_id` two meanings: Slack's own IDs in a query parameter, its `slch_` / `slws_` IDs in a body or a response, where Slack's own IDs are under `slack` (guide, IDs). The provider takes the body shape everywhere: the channel resource and data source hold `slack = { workspace_id, channel_id }`, the workspace settings resource and each item of `anthropic_claude_tag_slack_workspaces` hold `slack = { workspace_id }` (also the list's filter), and a top-level `slack_channel_id` / `slack_workspace_id` is always a `slch_` / `slws_` ID (`anthropic_claude_tag_bundle_target`). Keep that rule for any new attribute. `RequiresReplace` sits on the `slack` object of both resources.

**The five settings** (`settings.go`): `enabled`, `instructions`, `model`, `environment_id`, `guest_policy` (a string here, `{"type": ...}` on the wire). In the resources they are Optional, not Computed, and the configuration owns all five: a setting it does not declare is cleared on the level (sent as `null`), as the guide's "Keep configuration in version control" workflow says. `settingsPatch(plan, stored)` sends only what differs, `null` for what the plan drops; an empty patch sends nothing. Load-bearing details:
- `instructions` compare after `strings.TrimSpace`, and `settingsFromAPI` keeps the configuration's text when the API's equals it trimmed, because the API counts (and the fake assumes it stores) the trimmed text: without that a heredoc's final newline is a perpetual diff or an inconsistent result after apply. Blank text clears the setting on the API side, so the validator refuses it.
- `environment_id` takes an active `env_` environment of the Claude Enterprise organization. Whether an `anthropic_environment` created with a Claude Console workspace key is accepted is not verified, so the descriptions say so and nothing claims it works.
- A `ccpool_` runner pool in `environment_id` cannot be set, changed or cleared through the API (400 with no error_code). `runnerPoolConflict` refuses such a patch before sending, with a message that says to declare the pool's ID; `clearAllPatch` (workspace destroy) skips it with a warning.
- Unrecognized `guest_policy` types and error codes are kept as read (guide, Unrecognized values); the `OneOf` validator applies to the configuration only.

**Channel resource.** Create looks the channel up by its Slack IDs first (a 404 there, a Grid workspace not set up, counts as "not set up"), then posts the set-up request with the patch against what the channel stores: an existing channel is adopted and gets only the differing settings, and nothing is sent when it already stores the plan. Delete is refused by Claude Tag while `enabled` resolves to true (`slack_channel_enabled`); the provider does **not** turn Claude off by itself to get past that guard (the guide presents it as protection against removing a channel in use, and removal deletes sessions and memory): the diagnostic says to apply `enabled = false` first, or to use a `removed` block. A group DM or a channel holding a runner pool cannot be removed (400, no error_code). A set-up request whose settings are refused leaves the channel set up (`slack_channel_set_up_*`, ID in `error.details.slack_channel_id`); the next apply finds and adopts it.

**404 on refresh** (`readFailure`): a 404 without an error_code is either the object gone or the whole API reading as nonexistent (no beta, API not enabled). As the guide prescribes, the provider lists the workspaces (`?limit=1`, names nothing): 200 means gone (RemoveResource), anything else is an error that keeps the state. A 404 on delete is success.

**Read-only mode** (claude.ai's "API / Terraform read-only mode") does not make the API read-only: claude.ai and Slack refuse a person's changes while it is on. It is not a provider error case; the docs recommend it. The API's own write refusals are `claude_tag_writes_not_enabled` and `compliance_configuration_restricted` (403), which `errorHints` explains.

**Workspace settings resource.** Named `_settings` because it neither creates nor removes the workspace it configures, like `anthropic_compliance_settings`: no endpoint sets a workspace up or removes one. Create finds it by Slack's ID (empty list: not set up; 404: not owned) and patches; Delete clears what it stores and leaves it connected. Its `id` is the workspace's `slws_` ID.

**Bundle target.** `slack_channel_id` / `slack_workspace_id` are the API's `slch_` / `slws_` IDs (the body meaning), exactly one, validated by prefix so Slack's own IDs fail at plan. Import is `<bundle_id>:<target_id>` (the `:` of the provider's other composite import IDs), since the target does not hold its Bundle's ID. The same pair always has the same `btgt_` ID, and attaching an attached pair returns it (adoption).

**Data sources.** `anthropic_claude_tag_slack_channel` takes `id` or `slack` (exactly one). `anthropic_claude_tag_slack_workspaces` returns `slack_workspaces` (not `workspaces`, which `anthropic_workspaces` uses for Console workspaces). `include_inherited` switches to what applies in a level. `sources` (where each value comes from) is not mapped yet; a follow-up if audits need it. Bundles are read-only in the API.

**Tests.** `fake_test.go` is the fake Claude Tag API (levels, Slack defaults, resolution of inherited values, Bundles and targets, read-only mode for a person's changes, error codes); each behaviour cites its guide section. `*_fake_test.go` drive everything through `resource.UnitTest`; `settings_internal_test.go` covers the patch, the runner pool, the validator and `listAll`.
