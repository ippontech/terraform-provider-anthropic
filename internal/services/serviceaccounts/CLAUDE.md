# Service accounts service notes

Load-bearing details for `internal/services/serviceaccounts/`: the `anthropic_service_account` and `anthropic_service_account_workspace` resources and the `anthropic_service_account(s)` / `anthropic_service_account_workspaces` data sources (`client.Beta.Organization.ServiceAccounts`, OAuth `org:admin` bearer client). The root `CLAUDE.md` still applies; where a note here says "see above" or "see below" and the target is not in this file, it is a section of the root `CLAUDE.md`. Record new details about this service here, not in the root file. The WIF staleness probe that justifies `awaitServiceAccountUpdateVisible` is documented in `internal/services/federation/CLAUDE.md`.

**Resources:**
- `anthropic_service_account` (`internal/services/serviceaccounts/service_account_resource.go`) — manages a WIF service account: a pure identity (`svac_...`) that federation rules target, carrying no authorization of its own (Beta managed-agents API; `client.Beta.Organization.ServiceAccounts`); requires the OAuth `org:admin` bearer client (`pd.OAuthClient`), not Admin API keys; `name` is `RequiresReplace` (no `name` field on update); `organization_role` (`developer`/`admin`, Optional+Computed) is only resent on `Update` when it actually changed from state, since resending an unchanged value is rejected by the API for a non-interactive credential; no hard-delete endpoint — destroy always archives; `Update` applies the same defensive read-after-write consistency wait as vaults (see below)
- `anthropic_service_account_workspace` (`internal/services/serviceaccounts/service_account_workspace_resource.go`) — assigns a WIF service account to a workspace with a non-billing role (`client.Beta.Organization.ServiceAccounts.Workspaces`; OAuth `org:admin` client); composite ID `<service_account_id>:<workspace_id>`; the two IDs are `RequiresReplace`, while `workspace_role` is updated in place through the **workspace-side** endpoint `client.Beta.Organization.Workspaces.ServiceAccounts.Update` (`POST /v1/organizations/workspaces/{workspace_id}/service_accounts/{service_account_id}`, explicit memberships only; a 404 there means the membership is gone since the plan, and Update adds it back with the planned role, as the former replace did; the state is the plan, not the update response, so an unprobed response shape cannot cause an inconsistent result), followed by a best-effort `awaitServiceAccountWorkspaceRoleVisible` (5s/200ms consts as arguments, polls the list Read uses until the role matches under a context bounded by the timeout, so a slow or throttled list is cut off at the deadline, stops on 401/403/404 or a membership no longer listed; added preemptively, the endpoint was not probed); Delete is a hard remove; Read pages the membership list and **skips implicit entries** (every service account implicitly belongs to the org default workspace), so an explicit membership removed out-of-band surfaces as drift; ⚠️ positional-ID trap in both directions: `ServiceAccounts.Workspaces.Remove(ctx, workspaceID, params{ServiceAccountID})` takes the workspace ID positionally while `Workspaces.ServiceAccounts.Update(ctx, serviceAccountID, params{WorkspaceID})` takes the service account ID — each call is wrapped in a helper with the natural (service account, workspace) order and pinned by a URL-asserting unit test
