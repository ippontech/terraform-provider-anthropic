# Webhooks service notes

Load-bearing details for `internal/services/webhooks/`: the experimental `anthropic_webhook` resource (Managed Agents workspace webhook endpoints, raw `Execute` calls on the standard `*anthropic.Client`, beta header `managed-agents-2026-04-01` on every call via `doWebhookRequest`, standard key or the `aws` block). The root `CLAUDE.md` still applies; where a note here says "see above" or "see below" and the target is not in this file, it is a section of the root `CLAUDE.md`. Record new details about this service here, not in the root file.

**Resources:**
- `anthropic_webhook` (`internal/services/webhooks/webhook_resource.go`) — manages a workspace webhook endpoint (`/v1/webhooks[/{id}]`, `POST …/{id}/regenerate_signing_secret`). Experimental: Anthropic documents the [webhooks](https://platform.claude.com/docs/en/managed-agents/webhooks) as registered in the Console only, the API reference has no routes and no SDK manages them; the routes come from the Claude Platform on AWS IAM actions page (`CreateWebhook`, `GetWebhook`, `ListWebhooks`, `UpdateWebhook`, `DeleteWebhook`, `RotateWebhookSecret`) and the shapes mirror `anthropic_organization_webhook`, whose behaviour this resource copies (see `internal/services/organizationwebhooks/CLAUDE.md`): returned-once `signing_secret` regenerated through `signing_secret_version` (`signingSecretPlanModifier`, null after import), `enabled` ↔ `state` with a second call when the create response differs, `name`/`description` Optional+Computed, Update sends only changed fields and updates before regenerating. Differences: the request helper uses `client.Execute` with a `*[]byte` destination so the SDK carries auth, SigV4 and the workspace header; `isNotFound` matches `*anthropic.Error` 404 (gateway route-404s become `UnservedRouteError` through `platform.NotFoundGuard` and so never count as deleted); `enabled_events` is validated against `webhookEventTypes`, the 38 types listed on the webhooks page (the one list to extend; the SDK's extra session event types are not webhook events); after a regeneration Update always reads the endpoint back, because the regeneration moves `updated_at` past the update response (measured on AWS, otherwise the next plan shows `updated_at` drift). Every write holds the package-level `webhookWrites` mutex, as for organization webhooks: parallel applies of several endpoints in one workspace should not race. A 404 on Read or Delete counts as deleted only when `GET /v1/webhooks?limit=1` answers (`webhooksUnavailable`), so a retired beta or a wrong workspace does not drop the signing secret.

**Verification:** live on Claude Platform on AWS (2026-11-12, staging workspace, SigV4): create, rename, events change, disable/enable, regeneration alone and combined with an update, import (null secret, then a regeneration through `signing_secret_version`), destroy, import of the deleted ID refused; empty plan after each step. CloudTrail showed `CreateWebhook`, `GetWebhook`, `UpdateWebhook`, `RotateWebhookSecret`. Not verified on the Claude API (no first-party test credentials) nor on Google Cloud (`gcWebhooks` in the registry). No acceptance test: httptest unit tests (beta header asserted on every call) + `command = plan` native test.
