# Webhooks service notes

Load-bearing details for `internal/services/webhooks/`: the experimental `anthropic_webhook` resource (Managed Agents workspace webhook endpoints, raw `Execute` calls on the standard `*anthropic.Client`, beta header `managed-agents-2026-04-01` on every call via `doWebhookRequest`, standard key or the `aws` block). The root `CLAUDE.md` still applies; where a note here says "see above" or "see below" and the target is not in this file, it is a section of the root `CLAUDE.md`. Record new details about this service here, not in the root file.

**Resources:**
- `anthropic_webhook` (`internal/services/webhooks/webhook_resource.go`) — manages a workspace webhook endpoint (`/v1/webhooks[/{id}]`, `POST …/{id}/regenerate_signing_secret`). Experimental: Anthropic documents the [webhooks](https://platform.claude.com/docs/en/managed-agents/webhooks) as registered in the Console only, the API reference has no routes and no SDK manages them; the routes come from the Claude Platform on AWS IAM actions page (`CreateWebhook`, `GetWebhook`, `ListWebhooks`, `UpdateWebhook`, `DeleteWebhook`, `RotateWebhookSecret`) and the shapes mirror `anthropic_organization_webhook`, whose behaviour this resource copies (see `internal/services/organizationwebhooks/CLAUDE.md`): returned-once `signing_secret` regenerated through `signing_secret_version` (`signingSecretPlanModifier`, null after import), `enabled` ↔ `state` with a second call when the create response differs, `name`/`description` Optional+Computed, Update sends only changed fields and updates before regenerating. Differences: the request helper uses `client.Execute` with a `*[]byte` destination so the SDK carries auth, SigV4 and the workspace header, relative paths (`v1/webhooks`, as `internal/admin` writes them, so a base URL with a path keeps it) and a 60s per-attempt timeout (`webhookAttemptTimeout`, the Admin client's `attemptTimeout`), plus a 90s bound on a whole write once it holds the mutex (`webhookWriteTimeout`: attempts, SDK retries and backoff); the create is sent with `option.WithMaxRetries(0)` through `provretry.CreateRetrying429`, which resends only a 429, since a 408/409/5xx or a dropped connection may follow a create that landed and a replay would leave an untracked endpoint with a secret nobody holds (the Admin client the org resource uses never replays a POST either); `isNotFound` matches `*anthropic.Error` 404 (gateway route-404s become `UnservedRouteError` through `platform.NotFoundGuard` and so never count as deleted); `enabled_events` only requires one element: the API validates the types itself and accepts more than the webhooks page lists (47 probed, `session.{created,…}` and `user_profile.*` included), answering 400 with the valid values; the create decodes `id` and `signing_secret` before the rest of the response, so a shape change saves the endpoint (tainted) with its secret instead of orphaning it, and an empty `id` is an error; after a regeneration Update always reads the endpoint back, because the regeneration moves `updated_at` past the update response (measured on AWS, otherwise the next plan shows `updated_at` drift). Every write holds the package-level `webhookWrites` mutex, as for organization webhooks: parallel applies of several endpoints in one workspace should not race. A 404 on Read or Delete counts as deleted only when `GET /v1/webhooks?limit=1` answers (`webhooksUnavailable`), so a retired beta does not drop the signing secret; `unconfirmedDeletion` words the error by the list's status (404: retired beta or unserved route, 403: missing `ListWebhooks`); a provider pointed at another workspace still drops the endpoint, as for other workspace resources, since that workspace's list answers (the docs say so).

**Verification:** live on Claude Platform on AWS (2026-11-12, staging workspace, SigV4): create, rename, events change, disable/enable, regeneration alone and combined with an update, import (null secret, then a regeneration through `signing_secret_version`), destroy, import of the deleted ID refused; empty plan after each step. CloudTrail showed `CreateWebhook`, `GetWebhook`, `UpdateWebhook`, `RotateWebhookSecret`. Claude API: probed live with the standard key on 2026-11-12 (see the measurements in #537) and covered by the acceptance tests in `webhook_resource_test.go`: create, import (null secret, then regeneration through `signing_secret_version`), in-place updates of every mutable attribute, enable/disable checked out of band, rotation alone and combined with a rename, and `workspace_id` routing with the multi-workspace key (terraform-tests-2). They point at `example.com`, subscribe to `vault_credential.refresh_failed` (never emitted in the test workspaces) and stay disabled outside the toggle step; each draws its own URL, since enabled URLs are unique across the organization (409). Unavailable on Google Cloud (`gcWebhooks` in the registry): the webhooks page lists the Claude API and AWS only. Re-tested on AWS after the second review: create with `enabled = false` and an event type the page does not list (`session.created`), an unknown type refused by the API (400) with the state kept, enable plus rotation, empty plan after each step. The native test stays `command = plan`: the public example subscribes to session events and is enabled, so applying it would deliver real events to `example.com`.
