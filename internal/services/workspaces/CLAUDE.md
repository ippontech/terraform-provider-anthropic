# Workspaces service notes

Load-bearing details for `internal/services/workspaces/`: the `anthropic_workspace`, `anthropic_workspace_member` and `anthropic_workspace_rate_limit` resources and the `anthropic_workspace(s)`, `anthropic_workspace_member(s)` and `anthropic_workspace_rate_limits` data sources (Admin API, `internal/admin` client). The root `CLAUDE.md` still applies; where a note here says "see above" or "see below" and the target is not in this file, it is a section of the root `CLAUDE.md`. Record new details about this service here, not in the root file.

**Resources:**
- `anthropic_workspace` (`internal/services/workspaces/workspace_resource.go`) — manages workspaces (admin API; update is `POST /v1/organizations/workspaces/{id}`). Beyond `name`/`data_residency`: `tags` (map, Optional+Computed; keys starting with `anthropic` rejected at plan time, case-insensitive; update sends planned keys plus `null` for every key present in state and absent from the plan via `buildWorkspaceTagsPatch`, and omits `tags` when unchanged; measured live on 2026-10-08 (reversible probe on `terraform-tests`): the API **merges** tags, a per-key `null` deletes the key, `{}` is a **no-op** (so `tags = {}` must send `null` for each prior key), a whole-map `null` is a 400 ("At least one field must be provided") and an `anthropic`-prefixed key is rejected server-side with a 400 too; omitting the attribute keeps the server's tags, `tags = {}` clears them), `external_key_id` (CMEK `ekey_…`, write-once: Optional+Computed with `UseStateForUnknown` **then** `RequiresReplaceIf` (`externalKeyRequiresReplace`: only when an attached key changes or is removed), so a key attached from the Console does not force a destructive replace and attaching a first key to an existing workspace is an in-place update, since the Update reference lists `external_key_id` as a body parameter; sent on update only when state is null and the plan sets it, via `buildWorkspaceExternalKeyUpdate`), and Computed `compartment_id`, `user_profile_id`, `inference_data_retention{type}`. The last two exist only in the live payload (probed 2026-10-08, only `{"type": "disabled"}` observed): neither the SDK `BetaWorkspace` type (v1.67.0 then, v1.84.0 still) nor the reference pages list them, so the object is decoded leniently and documented as observed, not specified. Same five attributes are Computed on the `workspace`/`workspaces` data sources. A state created before these attributes existed plans `No changes` with the new schema (checked with an import under the old binary, then a plan under the new one)
- `anthropic_workspace_member` (`internal/services/workspaces/workspace_member_resource.go`) — assigns a user to a workspace with a given role (admin API); composite ID `<workspace_id>:<user_id>`; `workspace_billing` role rejected at plan time
- `anthropic_workspace_rate_limit` (`internal/services/workspaces/workspace_rate_limit_resource.go`) — sets a workspace's rate-limit overrides for one group (admin API `POST /v1/organizations/workspaces/{workspace_id}/rate_limits/{rate_limit_id}`, not in SDK v1.67.0); `workspace_id`/`rate_limit_id` are `RequiresReplace`, composite ID `<workspace_id>:<rate_limit_id>`; `limits` is a required `map(number)` keyed by limiter type (validated against the 9 documented types, values 0..2^53-1 and never null, at least one key). The endpoint only touches the types it names (integer sets, `null` clears), so the resource owns exactly its keys: `buildWorkspaceRateLimitPatch` sends planned values plus `null` for owned keys the plan dropped, Delete sends `null` for every owned key (no call if none; 404 tolerated), and Read lists **without** `include_inherited` and keeps only managed keys, so an override cleared out of band shows as drift (an empty map when the whole entry is gone). A list lagging behind a write looks the same to Read, so the owned keys are the state's plus the types Create and Update record in private state (`set_limit_types`, the planned values after each successful request): a destroy right after an apply still clears what the resource set. A recorded type in neither the state nor the plan can also be one cleared out of band and then removed from the configuration (no update ran to refresh the record), and set again since in the Console or by another resource, so Update and Delete list the group first (only when there is such a type) and leave it alone when the group holds another value than the recorded one (`ownedLimitTypes`; the same value is indistinguishable and is cleared). Import (null `limits`) takes every override of the group whose type is one of the 9 (`overridesToState`: an override of another type, which the list can carry, could not be declared in the configuration, so every apply would clear it), a sibling resource's types included (documented), and fails when the group has none. A third import-ID segment, `<workspace_id>:<rate_limit_id>:<type>[,<type>...]`, names the types to import (`importTypesPrivateKey` carries them from `ImportState` to the next `Read`, which keeps only them, fails if one has no override, then drops the key), so a resource sharing its group with another can be imported without taking the other's types; the id stays two segments. Two resources on one group update in parallel, so the docs tell users to move a type between them with `depends_on` or over two applies. Plan-only native test (#58); the live `TestAccWorkspaceRateLimitResource_inheritedValue` runs in CI with the Admin key: on `terraform-tests-2` it sets a `requests_per_minute` override equal to the inherited organization value, so it limits nothing even if left behind, checks the source turns `workspace`, re-imports with the three-segment ID, and checks the source is back to `organization` after destroy; the doc's `rate_limit_id` lookup goes through `anthropic_workspace_rate_limits` with `include_inherited = true`, reads `models` through `coalesce` (null for a group without a visible model) and passes `terraform validate`

**Data sources:**
- `anthropic_workspace` (`internal/services/workspaces/workspace_data_source.go`) — fetches a single workspace by ID (admin API)
- `anthropic_workspaces` (`internal/services/workspaces/workspaces_data_source.go`) — lists all workspaces (admin API, transparent pagination); `include_archived` and `include_default` (the Default Workspace is listed only on request, and its real ID is what the Admin API reports in the `scope.workspace_id` of the API keys bound to it, whose `workspace_id` is null; the example finds it as the one workspace only the `include_default` list holds, since another workspace can be named "Default") are sent only when true, query built by `buildWorkspacesListQuery`
- `anthropic_workspace_member` (`internal/services/workspaces/workspace_member_data_source.go`) — fetches a single workspace member by workspace ID and user ID (admin API)
- `anthropic_workspace_members` (`internal/services/workspaces/workspace_members_data_source.go`) — lists all members of a workspace (admin API), with transparent pagination
- `anthropic_workspace_rate_limits` (`internal/services/workspaces/workspace_rate_limits_data_source.go`) — lists a workspace's rate limits (admin API) with optional `group_type` and `include_inherited` filters; by default only entries with at least one override, with `include_inherited = true` every group with organization limits (entries are never filtered client-side, each limit's `source.type` is `workspace` or `organization`). Each entry exposes `rate_limit_id` (the organization entry ID an override takes) and `group{id, type, display_name}`; `group_type` carries a `DeprecationMessage` (removed in API 2026-10-21). The rate-limit lists paginate with an opaque `page`/`next_page` cursor, **not** `after_id`/`has_more`: `listRateLimitPages` (which fails on a `next_page` already sent during the listing, rather than looping) and the `group` mapping live in `rate_limit_common.go`, shared by every rate-limit data source
